# 跨案例设计笔记

搭这 8 个应用的过程中反复踩到同一类坑，记下来避免下次再踩。

## 1. 状态放会话变量，不放 prompt

**反例**：把历史对话拼进 system prompt。

问题有三个：随轮次线性膨胀、模型会"改写"历史（尤其摘要型任务）、无法人工审阅和修正。

**做法**：用 Dify 的会话变量（`conversation_variables`）。它是强一致的键值存储，`over-write / append / clear` 三种写模式覆盖了绝大多数需求，而且在调试面板里能直接看到当前值。

判断标准很简单：**这个信息是"事实"还是"上下文"**？事实（用户过敏史、已填槽位）放变量；上下文（上一轮说了什么）可以交给对话历史。

## 2. 凡是模型输出的结构化数据，后面必须跟一个 Code 节点

这是这 8 个案例里出现频率最高的一条。

模型返回合法 JSON 的概率，随着输出长度和嵌套深度急剧下降。指望它"这次一定乖"是不现实的。所以：

- `nlp2sql` 里有两层解析（SQL 候选 + 图表参数），各自带默认值兜底；
- `code-translator` 里用 YAML → JSON 的工具转换 + 正则抽取双保险；
- 每个解析都写了 `except` 分支返回 `default_output`，**不抛异常**。

一个实用技巧：让模型用 ```` ```json ```` 围栏包住输出，然后用正则 `r"```json\s*([\s\S]*?)\s*```"` 提取。比 `json.loads` 直接解析整段文本鲁棒得多，因为模型总爱在 JSON 前后加一句"好的，这是结果："。

## 3. 能用确定性分支就别用模型判断

| 需求 | 错误做法 | 正确做法 |
| --- | --- | --- |
| 槽位填满了没有 | 问模型"信息够了吗" | TOD 策略返回 `InformationCollectionCompleted` 信号 |
| 澄清问到第几轮 | 问模型"还需要问吗" | `if-else` 判断 `dialogue_count == N` |
| 该压缩记忆了吗 | 问模型"要不要总结" | `dialogue_count % 3 == 0` |
| 该画什么图 | 让模型直接渲染 | 模型只输出类型枚举，路由交给条件分支 |

模型判断的价值在于处理**语义模糊**，不在于处理**计数和枚举**。用错地方既贵又不稳。

## 4. 迭代批处理优于单次长输出

`code-translator` 的核心技巧：翻译一个大文件时，不让模型一次吐完（必然被输出长度截断），而是：

1. 第一轮只生成**类/函数签名**的结构化描述（很短）；
2. 代码解析出签名列表；
3. `Iteration` 逐个函数生成实现；
4. 代码按原顺序合并成完整文件。

同理，`deep-researcher` 的检索也是"先抽关键词，再逐词检索"而不是"一段话查一次"。

**分而治之的判据**：如果一个任务的输出超过了模型单次输出预算的 60%，就该考虑拆分。

## 5. 每个 LLM 节点都要想好失败路径

失败有三种：空输出、格式错误、超时/限流。三种至少兜一种：

- **空输出**：下游加非空校验（`deep-researcher` 的 `条件分支 2` 检查 6 个变量是否非空）；
- **格式错误**：Code 节点给默认值（`nlp2sql` 的 `default_output`）；
- **超时**：目前没做，这是已知缺口。

Dify 的 `answer` 节点很适合做**兜底文案位**：主链路失败时输出一句"报告生成发生错误，请重试"，比让用户看到红色报错好得多。

## 6. 关于成本

多候选、反思重写、迭代检索，这些"高级"套路都是**成倍的成本**：

| 机制 | 成本倍数 | 适用场景 |
| --- | --- | --- |
| best-of-4 + judge | ~5x | 用户可感知的内容（话术、客服回复） |
| 三角度重写 | ~4x | 高风险领域（医疗、金融） |
| 逐词迭代检索 | ~Nx（N=关键词数） | 研究型任务，可接受分钟级延迟 |
| 单轮直出 | 1x | 内部工具、低风险场景 |

**结论：这些机制不该默认开**。应该按场景做开关，而不是全项目统一上。

## 7. 如果不用 Dify，我会怎么做

面试常被问到这个，我的答案：

- **编排层**：用 LangGraph 或自己写状态机，把"节点 + 边"显式建模成 `State → Node → State` 的转移函数，持久化到 Redis/Postgres，支持断点续跑。
- **工具调用**：走标准 function calling，工具用 JSON Schema 描述，注册到统一 registry，而不是每个插件一套参数格式。
- **记忆**：短期用会话窗口 + 摘要，长期用向量库 + 结构化档案双写；检索时先走结构化过滤（过敏史这类硬约束），再走向量召回。
- **结构化输出**：优先用模型的 `response_format=json_schema` 约束，仍必须保留代码层容错。
- **可观测**：每一步的输入输出、token 数、延迟都要落库，否则线上问题无法定位 —— 这是 Dify 这类平台目前最欠缺的部分。

换句话说：**Dify 帮我省掉了编排的脚手架，但没省掉设计决策**。而这个项目真正想练的，是设计决策。
